## Purpose

The Undo & Redo feature provides history-based recovery of edit operations in Batch Edit mode. It maintains a stack of user actions (cell edits, row additions, row deletions, paste operations, and auto-fill operations) and allows users to reverse or reapply those actions using keyboard shortcuts (Ctrl+Z, Ctrl+Y, Ctrl+Shift+Z), toolbar buttons, or public API methods. This specification documents the complete lifecycle, action types, state management, history cleanup rules, and cross-feature interaction guarantees.

## Requirements

### Requirement: EnableUndoRedo

The grid's Undo/Redo capability SHALL be activated only when `GridEditSettings.EnableUndoRedo` is `true`. Undo/Redo SHALL be disabled by default and only supported in `EditMode.Batch`.

#### Scenario: UndoRedoDisabledByDefault
- **GIVEN** a grid with `<GridEditSettings>` component configured but `EnableUndoRedo` not set
- **WHEN** a user performs a batch edit operation (cell edit, row add, row delete)
- **THEN** no undo or redo history is maintained, and keyboard shortcuts (Ctrl+Z, Ctrl+Y) have no effect

#### Scenario: UndoRedoEnabledViaParameter
- **GIVEN** `<GridEditSettings Mode="EditMode.Batch" EnableUndoRedo="true">` is set
- **WHEN** a user edits a cell in batch mode
- **THEN** the action is recorded in the Undo stack, `UndoCount` increments, and `IsUndoAvailable` is `true`

#### Scenario: UndoRedoNotSupportedInNormalMode
- **GIVEN** `Mode="EditMode.Normal"` and `EnableUndoRedo="true"`
- **WHEN** a user edits a row
- **THEN** Undo/Redo functionality is silently disabled; the undo/redo stacks remain empty

#### Scenario: UndoRedoNotSupportedInDialogMode
- **GIVEN** `Mode="EditMode.Dialog"` and `EnableUndoRedo="true"`
- **WHEN** a user edits a row in dialog mode
- **THEN** Undo/Redo functionality is silently disabled; the undo/redo stacks remain empty

#### Scenario: EditModeValidationOnInitialization
- **GIVEN** `EnableUndoRedo="true"` is set at grid initialization
- **WHEN** the grid checks the current `Mode`
- **THEN** if `Mode` is Normal or Dialog, undo/redo is silently disabled with no error raised; if `Mode` is Batch, undo/redo is enabled

#### Scenario: UndoRedoTogglingAtRuntime
- **GIVEN** grid is in Batch mode with `EnableUndoRedo="true"` and undo history exists
- **WHEN** `EnableUndoRedo` is set to `false` dynamically
- **THEN** the Undo and Redo stacks are automatically cleared, and `UndoCount`/`RedoCount` become 0

### Requirement: UndoRedoLimit

The grid SHALL maintain a configurable maximum size for the Undo and Redo stacks. When the limit is exceeded, the oldest actions are discarded.

#### Scenario: UndoRedoLimitDefault
- **GIVEN** `GridEditSettings.UndoRedoLimit` is not set
- **WHEN** the grid is initialized
- **THEN** `UndoRedoLimit` defaults to `20`

#### Scenario: UndoStackExceedsLimit
- **GIVEN** `UndoRedoLimit="10"` and the Undo stack contains 10 actions
- **WHEN** a user performs an 11th action
- **THEN** the oldest action is removed from the Undo stack, and the new action is added to the top

#### Scenario: CustomUndoRedoLimit
- **GIVEN** `UndoRedoLimit="50"`
- **WHEN** a user performs 45 consecutive edits
- **THEN** all 45 actions are maintained in the Undo stack, and `UndoCount` is 45

### Requirement: StackPerformanceOptimization

The grid's Undo/Redo stack operations SHALL maintain O(1) time complexity for push/pop operations and provide memory-efficient management for large datasets.

#### Scenario: StackPushPopPerformance
- **GIVEN** a grid with 1000+ rows and `UndoRedoLimit="20"`
- **WHEN** a user performs 100 consecutive cell edits
- **THEN** each edit/undo/redo completes in <10ms, and stack operations do not block the UI

#### Scenario: LargeDatasetStackManagement
- **GIVEN** a grid with 10,000+ rows and `UndoRedoLimit="10"`
- **WHEN** user performs rapid edits on multiple cells
- **THEN** oldest actions are removed in FIFO order when limit is exceeded, and memory usage remains bounded

#### Scenario: MemoryOptimizationOnClear
- **GIVEN** Undo and Redo stacks contain 100 actions with associated data
- **WHEN** `ClearUndoRedoAsync()` is called
- **THEN** all allocated memory is released and garbage collected

### Requirement: SupportedActionTypes

The grid SHALL track and support undo/redo for five action types: CellEdit, RowAdd, RowDelete, Paste, and AutoFill.

#### Scenario: CellEditAction
- **GIVEN** a batch-edit grid with a cell in editable state
- **WHEN** a user changes a cell value and moves to the next cell
- **THEN** a `CellEdit` action is recorded with the original and new values

#### Scenario: RowAddAction
- **GIVEN** `AllowAdding="true"` and a new row is added via `AddRecord` or toolbar button
- **WHEN** the user fills in fields and moves to the next row
- **THEN** a `RowAdd` action is recorded with the newly added row data

#### Scenario: RowDeleteAction
- **GIVEN** `AllowDeleting="true"` and a row is deleted via `DeleteRecord` or toolbar button
- **WHEN** the delete action completes
- **THEN** a `RowDelete` action is recorded with the original row data for restoration

#### Scenario: PasteAction
- **GIVEN** multiple cells are selected and paste (Ctrl+V) is executed
- **WHEN** the clipboard content is applied to the selected range
- **THEN** a single `Paste` action is recorded representing all pasted cells as an atomic operation

#### Scenario: PasteCSVFormatMultipleCells
- **GIVEN** clipboard contains CSV-formatted data (rows separated by \n, columns separated by \t)
- **WHEN** user pastes into a 5x5 range
- **THEN** data is parsed correctly, all 25 cells are updated, and a single `Paste` action captures the entire operation

#### Scenario: PasteWithTypeConversion
- **GIVEN** clipboard contains string values, but destination cells are numeric or date columns
- **WHEN** `UndoAsync()` is called after paste with type conversion
- **THEN** original values (before type conversion) are restored to the cells

#### Scenario: AutoFillAction
- **GIVEN** AutoFill feature is enabled and user drags the fill handle
- **WHEN** the auto-fill pattern completes
- **THEN** an `AutoFill` action is recorded with the filled cell range and values

### Requirement: UndoOperation

When `UndoAsync()` is invoked or Ctrl+Z is pressed, the grid SHALL remove the most recent action from the Undo stack, reverse its effect, and move it to the Redo stack.

#### Scenario: UndoSingleCellEdit
- **GIVEN** a cell was edited from "Original" to "Modified" and an Undo stack contains this `CellEdit` action
- **WHEN** `UndoAsync()` is called
- **THEN** the cell reverts to "Original", the action moves from Undo to Redo stack, `UndoCount` decrements, and `RedoCount` increments

#### Scenario: UndoRowAdd
- **GIVEN** a new row was added to the grid and an Undo stack contains the `RowAdd` action
- **WHEN** `UndoAsync()` is called
- **THEN** the row is removed from the grid's data collection, the action moves to the Redo stack, and the grid UI updates to reflect the removal

#### Scenario: UndoRowDelete
- **GIVEN** a row was deleted and an Undo stack contains the `RowDelete` action
- **WHEN** `UndoAsync()` is called
- **THEN** the row is restored to its original position in the grid's data collection, the action moves to the Redo stack, and the grid UI updates

#### Scenario: UndoPaste
- **GIVEN** a multi-cell paste operation was performed and an Undo stack contains the `Paste` action
- **WHEN** `UndoAsync()` is called
- **THEN** all pasted cells are reverted to their original values, the action moves to the Redo stack

#### Scenario: UndoWhenStackEmpty
- **GIVEN** the Undo stack is empty and `IsUndoAvailable` is `false`
- **WHEN** `UndoAsync()` is called or Ctrl+Z is pressed
- **THEN** no action occurs, the stacks remain unchanged, and no error is raised

#### Scenario: KeyboardShortcutCtrlZ
- **GIVEN** `EnableUndoRedo="true"` in a batch-edit grid
- **WHEN** user presses Ctrl+Z
- **THEN** `UndoAsync()` is internally invoked with the same behavior as calling the method

### Requirement: RedoOperation

When `RedoAsync()` is invoked or Ctrl+Y/Ctrl+Shift+Z is pressed, the grid SHALL remove the most recent action from the Redo stack, reapply its effect, and move it to the Undo stack.

#### Scenario: RedoSingleCellEdit
- **GIVEN** an Undo/Redo cycle has occurred: cell edited to "Modified", then Undo called (now in Redo stack)
- **WHEN** `RedoAsync()` is called
- **THEN** the cell is set back to "Modified", the action moves from Redo to Undo stack, `RedoCount` decrements, and `UndoCount` increments

#### Scenario: RedoRowAdd
- **GIVEN** a row was added, undone, and the `RowAdd` action is in the Redo stack
- **WHEN** `RedoAsync()` is called
- **THEN** the row is restored to the grid's data collection, the action moves to the Undo stack

#### Scenario: RedoRowDelete
- **GIVEN** a row was deleted, undone, and the `RowDelete` action is in the Redo stack
- **WHEN** `RedoAsync()` is called
- **THEN** the row is deleted again, the action moves to the Undo stack

#### Scenario: RedoWhenStackEmpty
- **GIVEN** the Redo stack is empty and `IsRedoAvailable` is `false`
- **WHEN** `RedoAsync()` is called or Ctrl+Y is pressed
- **THEN** no action occurs, the stacks remain unchanged

#### Scenario: KeyboardShortcutCtrlY
- **GIVEN** `EnableUndoRedo="true"` and Redo actions are available
- **WHEN** user presses Ctrl+Y
- **THEN** `RedoAsync()` is internally invoked with the same behavior

#### Scenario: KeyboardShortcutCtrlShiftZ
- **GIVEN** `EnableUndoRedo="true"` and Redo actions are available
- **WHEN** user presses Ctrl+Shift+Z
- **THEN** `RedoAsync()` is internally invoked (alternative shortcut)

### Requirement: KeyboardShortcutPriority

The grid's keyboard shortcuts for Undo/Redo SHALL only be active when the grid has focus and SHALL respect the edit mode state.

#### Scenario: KeyboardShortcutRequiresGridFocus
- **GIVEN** `EnableUndoRedo="true"` but the grid does not have focus (another input field is focused)
- **WHEN** user presses Ctrl+Z
- **THEN** the keyboard shortcut is not intercepted, and the focus remains on the external input

#### Scenario: UndoInBatchEditCellExitMode
- **GIVEN** a cell is actively in edit state (cursor blinking in input field) and user presses Ctrl+Z
- **WHEN** the keystroke is processed
- **THEN** the grid exits edit mode first (if configured), then Undo is applied

#### Scenario: EscapeExitEditBeforeUndo
- **GIVEN** a cell is in edit state
- **WHEN** user presses Escape to exit edit
- **THEN** the edit is cancelled (reverted to pre-edit value), and the next Ctrl+Z undoes the action before this edit

#### Scenario: KeyboardShortcutDisabledWhenGridDisabled
- **GIVEN** grid is disabled (disabled="disabled" or `AllowEditing="false"`)
- **WHEN** user presses Ctrl+Z or Ctrl+Y
- **THEN** keyboard shortcuts have no effect and no undo/redo occurs

### Requirement: ActionIdAndTraceability

Each Undo/Redo action SHALL be assigned a unique identifier and support diagnostic queries for tracking and tracing operations.

#### Scenario: UniqueActionIdAssignment
- **GIVEN** a user performs an edit action in batch mode
- **WHEN** the action is recorded in the Undo stack
- **THEN** it is assigned a unique `ActionId` (GUID or incremental integer)

#### Scenario: ActionIdConsistencyAcrossStacks
- **GIVEN** an action is created with `ActionId = "ABC123"` and placed in the Undo stack
- **WHEN** `UndoAsync()` is called and the action moves to the Redo stack
- **THEN** the `ActionId` remains "ABC123"

#### Scenario: GetActionByIdMethod
- **GIVEN** an action with `ActionId = "ABC123"` exists in Undo or Redo stack
- **WHEN** `GetActionById("ABC123")` is called
- **THEN** the action details are returned (type, affected cells, values)

#### Scenario: ActionIdInEventArguments
- **GIVEN** `ActionUndoing` or `ActionRedoing` event fires
- **WHEN** event handler accesses event arguments
- **THEN** the `ActionId` is included and can be logged for diagnostics

### Requirement: RedoStackClearOnNewEdit

When a new edit operation is performed after one or more Undo operations, the Redo stack SHALL be cleared completely.

#### Scenario: NewEditAfterUndo
- **GIVEN** Cell A was edited to "ValueA", then undone; Redo stack contains the Undo operation
- **WHEN** user edits Cell B to "ValueB"
- **THEN** Cell B edit is added to Undo stack, Redo stack is cleared, `RedoCount` becomes 0, and `IsRedoAvailable` is `false`

#### Scenario: UndoMultipleActionsRedoStackClear
- **GIVEN** 5 actions were performed and 3 were undone (3 actions in Redo stack)
- **WHEN** user edits a new cell
- **THEN** Redo stack is completely cleared, and the 3 previously undone actions cannot be re-applied

### Requirement: BulkActions

Bulk operations (Paste, AutoFill, multi-cell edit) SHALL be recorded as single atomic actions in the Undo/Redo stacks.

#### Scenario: PasteRecordedAsAtomicAction
- **GIVEN** a 5x5 range of cells is selected
- **WHEN** user pastes data from clipboard (Ctrl+V)
- **THEN** all 25 cells are updated via one `Paste` action; a single Undo reverts all 25 cells

#### Scenario: AutoFillRecordedAsAtomicAction
- **GIVEN** cells contain a series pattern (1, 2, 3) and AutoFill is enabled
- **WHEN** user drags the fill handle to row 10
- **THEN** the entire auto-fill operation is recorded as a single `AutoFill` action

### Requirement: TransactionalActionGrouping

The grid SHALL support grouping related edit operations into a single atomic action for undo/redo purposes, allowing multiple edits to be reversed with a single Undo command.

#### Scenario: GroupMultipleCellEditsAsAtomicAction
- **GIVEN** `BeginActionGroup()` is called, then user edits cells A1, A2, A3 in the same row, then `EndActionGroup()` is called
- **WHEN** `UndoAsync()` is invoked
- **THEN** all 3 cell edits are reversed atomically as a single action, and the Undo stack contains 1 grouped action instead of 3 individual actions

#### Scenario: GroupRowAddAndEditOperations
- **GIVEN** a new row is added via `BeginActionGroup()`, then multiple cells in that row are edited, then `EndActionGroup()` is called
- **WHEN** `UndoAsync()` is invoked
- **THEN** both the row add and all cell edits are reversed together

#### Scenario: ActionGroupNestingNotSupported
- **GIVEN** `BeginActionGroup()` is called, then `BeginActionGroup()` is called again before `EndActionGroup()`
- **WHEN** the second `BeginActionGroup()` is encountered
- **THEN** the call is silently ignored, and the existing group remains active

### Requirement: ValidationBehaviorDuringUndoRedo

The grid SHALL handle validation rules differently during Undo versus Redo operations to maintain data consistency.

#### Scenario: ValidationBypassedOnUndo
- **GIVEN** a cell contains a value that was valid when originally entered, but no longer passes current validation rules
- **WHEN** `UndoAsync()` is called to restore that value
- **THEN** validation rules are bypassed (not checked), and the value is restored without validation errors

#### Scenario: ValidationEnforcedOnRedo
- **GIVEN** a value was undone and now the Redo stack contains the action
- **WHEN** `RedoAsync()` is called to reapply that value
- **THEN** validation rules are enforced, and if the value fails validation, the Redo is cancelled and an event is raised

#### Scenario: UndoPreservesOriginalValidState
- **GIVEN** a cell edit changed a value from "Valid" to "Invalid", but the edit was allowed
- **WHEN** `UndoAsync()` is called
- **THEN** the value reverts to "Valid" without validation interference

### Requirement: ForeignKeyColumnUndoRedo

The grid SHALL correctly handle Undo/Redo for Foreign Key columns by restoring both the display value and the underlying foreign key identifier.

#### Scenario: UndoForeignKeyColumnEdit
- **GIVEN** a Foreign Key column displays "Product A" (FK ID: 101), user changes it to "Product B" (FK ID: 102)
- **WHEN** `UndoAsync()` is called
- **THEN** both the display value ("Product A") and the FK ID (101) are restored

#### Scenario: RedoForeignKeyColumnEdit
- **GIVEN** a FK column was undone and the original value is in the Redo stack
- **WHEN** `RedoAsync()` is called
- **THEN** both the display value and FK ID are re-applied from the Redo stack

#### Scenario: ForeignKeyValidationDuringUndo
- **GIVEN** a FK column references an external data source that may have changed
- **WHEN** `UndoAsync()` restores a FK value whose referenced record no longer exists
- **THEN** the value is still restored (data consistency prioritized over referential integrity during undo)

- **GIVEN** edit data contains complex field paths like `Company.Department.Budget`
- **WHEN** `UndoAsync()` or `RedoAsync()` processes the action
- **THEN** the full path is correctly resolved and the nested value is updated

### Requirement: ErrorRecoveryAndStateConsistency

The grid SHALL maintain a consistent state and recover gracefully if an Undo/Redo operation encounters an error mid-operation.

#### Scenario: UndoFailureStateRecovery
- **GIVEN** an Undo operation begins but encounters an error during data restoration (e.g., invalid data type)
- **WHEN** the error occurs
- **THEN** the grid returns to its previous consistent state, the stacks are not modified, and an error event is raised

#### Scenario: PartialUndoNotAllowed
- **GIVEN** a grouped action contains 5 edits and error occurs on the 3rd edit during Undo
- **WHEN** the error occurs
- **THEN** the entire group undo is rolled back, all 5 edits remain in the Undo stack, and no partial reversion occurs

#### Scenario: RedoFailureRollback
- **GIVEN** a Redo operation fails due to validation or data constraints
- **WHEN** the error occurs
- **THEN** the action remains in the Redo stack, the grid data is not modified, and the user can attempt Redo again

### Requirement: HistoryCleanup

The Undo and Redo stacks SHALL be automatically cleared when batch operations are finalized or the grid is refreshed.

#### Scenario: ClearHistoryOnBatchSave
- **GIVEN** user is in batch edit mode with `UndoCount > 0`
- **WHEN** `SaveBatch()` or grid's batch save toolbar button is clicked
- **THEN** the batch save completes, the Undo stack is cleared, the Redo stack is cleared, `UndoCount` and `RedoCount` are 0

#### Scenario: ClearHistoryOnBatchCancel
- **GIVEN** user is in batch edit mode with pending edits and undo/redo stacks populated
- **WHEN** `CancelBatch()` or grid's batch cancel toolbar button is clicked
- **THEN** all pending changes are discarded, the Undo and Redo stacks are cleared, `UndoCount` and `RedoCount` are 0

#### Scenario: ClearHistoryOnGridRefresh
- **GIVEN** batch edit mode is active with `UndoCount > 0`
- **WHEN** `Refresh()` or `RefreshAsync()` is called
- **THEN** the grid's data is refreshed, the Undo and Redo stacks are cleared

#### Scenario: ClearHistoryOnDataSourceReload
- **GIVEN** batch edit mode is active with edits pending
- **WHEN** `DataSource` property is changed or a new data reload is triggered
- **THEN** the Undo and Redo stacks are automatically cleared before the new data is bound

#### Scenario: UndoAsyncMethod

#### Scenario: ClearUndoRedoAsyncMethod
- **GIVEN** Undo and Redo stacks contain actions
- **WHEN** `await grid.ClearUndoRedoAsync()` is called
- **THEN** both stacks are cleared, `UndoCount` and `RedoCount` become 0, `IsUndoAvailable` and `IsRedoAvailable` are both `false`

### Requirement: UndoRedoEvents

The grid SHALL raise events before and after undo/redo operations to allow application-level hooks and validation.

#### Scenario: ActionUndoingEvent
- **GIVEN** a pending Undo action exists
- **WHEN** `UndoAsync()` is invoked
- **THEN** the `ActionUndoing` event is raised before the undo occurs, allowing cancellation via `Cancel` property

#### Scenario: ActionUndoingEventCancel
- **GIVEN** a handler for `ActionUndoing` that sets `Cancel = true`
- **WHEN** `UndoAsync()` is called
- **THEN** the undo operation is cancelled, stacks remain unchanged, and `ActionUndone` is not raised

#### Scenario: ActionUndoneEvent
- **GIVEN** an Undo operation completes successfully
- **WHEN** `UndoAsync()` finishes
- **THEN** the `ActionUndone` event is raised after the undo, allowing post-operation cleanup

#### Scenario: ActionRedoingEvent
- **GIVEN** a pending Redo action exists
- **WHEN** `RedoAsync()` is invoked
- **THEN** the `ActionRedoing` event is raised before the redo occurs, allowing cancellation

#### Scenario: ActionRedoingEventCancel
- **GIVEN** a handler for `ActionRedoing` that sets `Cancel = true`
- **WHEN** `RedoAsync()` is called
- **THEN** the redo operation is cancelled, stacks remain unchanged, and `ActionRedone` is not raised

#### Scenario: ActionRedoneEvent
- **GIVEN** a Redo operation completes successfully
- **WHEN** `RedoAsync()` finishes
- **THEN** the `ActionRedone` event is raised after the redo

#### Scenario: EventArgumentsContainActionMetadata
- **GIVEN** an Undo operation is about to occur
- **WHEN** `ActionUndoing` event fires
- **THEN** event arguments include: `ActionId` (unique identifier), `ActionType` (CellEdit/RowAdd/etc.), `PreviousState` (pre-undo data), `TargetCells` (affected cell coordinates)

#### Scenario: ActionUndoneEventArgumentsAvailable
- **GIVEN** an Undo operation completes successfully
- **WHEN** `ActionUndone` event fires
- **THEN** event arguments include: `ActionId`, `CurrentState` (post-undo data), `AffectedRowIndices` (rows impacted by undo)

#### Scenario: EventArgumentsContainRedoingMetadata
- **GIVEN** a Redo operation is about to occur
- **WHEN** `ActionRedoing` event fires
- **THEN** event arguments include all metadata similar to `ActionUndoing` but for the redo operation

### Requirement: CrossFeatureInteraction_Filtering

Undo/Redo operations SHALL work correctly when Filter Bar or Filter Menu is active.

#### Scenario: UndoEditWithFiltering
- **GIVEN** grid has a filter applied (e.g., "City = 'NYC'") and a cell outside the filter predicate is edited
- **WHEN** `UndoAsync()` is called

- **THEN** the row is removed, and the filter remains active

#### Scenario: UndoRowDeleteWithFiltering
- **GIVEN** grid is filtered and a row matching the filter is deleted
- **WHEN** `UndoAsync()` is called
- **THEN** the row is restored and appears in the filtered view

- **WHEN** `UndoAsync()` is called to restore the original value

#### Scenario: UndoRowDeleteOutsideFilterPredicate
- **GIVEN** grid is filtered and a row outside the filter predicate is deleted
- **WHEN** `UndoAsync()` is called
- **THEN** the row is restored to the data collection, but it doesn't appear in the current filtered view

### Requirement: MemoryManagementStrategy

The grid's Undo/Redo implementation SHALL manage memory efficiently and provide guidance on configuration for large datasets.

#### Scenario: ActionMemoryFootprint
- **GIVEN** each action stores: OriginalValue, NewValue, ColumnField, RowIndex, Timestamp, ActionId, Metadata
- **WHEN** actions accumulate in the Undo stack
- **THEN** each action requires approximately 40-100 bytes of memory (depending on value size)

#### Scenario: LargeDatasetStackRecommendation
- **GIVEN** a grid with 100K+ rows and large cell values (complex objects)
- **WHEN** developer configures `UndoRedoLimit`
- **THEN** recommendation is to use `UndoRedoLimit="5"` to `UndoRedoLimit="10"` to maintain reasonable memory footprint

#### Scenario: MemoryClearedOnStackClear
- **GIVEN** Undo and Redo stacks contain 100 actions with accumulated data
- **WHEN** `ClearUndoRedoAsync()` is called or batch save completes
- **THEN** all action data is dereferenced and eligible for garbage collection

#### Scenario: StackDataNotSerializedToDisk
- **GIVEN** Undo/Redo is enabled on the grid
- **WHEN** page is closed or grid is disposed
- **THEN** all stack data is cleared from memory (no persistence to localStorage or IndexedDB by default)

### Requirement: EventSequencingAndCancellation

The grid SHALL raise Undo/Redo events in a strict, predictable order, allowing event handlers to intercept and cancel operations at the correct phase.

#### Scenario: StrictEventOrderingOnUndo
- **GIVEN** `UndoAsync()` is called
- **WHEN** the operation begins
- **THEN** events are raised in this exact order:
  1. `ActionUndoing` (before state change, cancellable)
  2. Data reversal occurs
  3. `ActionUndone` (after state change, not cancellable)
  4. UI refresh completes

#### Scenario: ActionUndoingEventOrderingWithMultipleHandlers
- **GIVEN** multiple handlers are subscribed to `ActionUndoing`
- **WHEN** `UndoAsync()` is called
- **THEN** handlers execute in subscription order, and the first handler to set `Cancel=true` prevents all subsequent handlers and the undo operation

#### Scenario: ActionUndoneNotCancellable
- **GIVEN** `ActionUndone` event is raised after a successful undo
- **WHEN** event handler tries to set `Cancel=true`
- **THEN** the property is ignored (or throws an exception), as the undo has already committed

#### Scenario: RedoEventSequencingConsistent
- **GIVEN** `RedoAsync()` is called
- **WHEN** the operation begins
- **THEN** the event sequence mirrors Undo: `ActionRedoing` (cancellable) → reapplication → `ActionRedone` (non-cancellable)

## Limitations & Constraints

The following operations are **NOT** tracked or undoable in the Undo/Redo system:

### UI-Only Operations (Not Tracked)
- ❌ **Sorting Changes** - Column sort order is UI state only, not a data change
  - Rationale: User can reapply sort without affecting edited data
- ❌ **Filtering Changes** - Filter predicates are UI state only, not data changes
  - Rationale: Undo/redo reverses data edits, not filter visibility
- ❌ **Column Reordering** - Column order is UI state only
  - Rationale: Reordering columns doesn't modify underlying data
- ❌ **Column Resizing** - Column width is UI state only
  - Rationale: Grid state persistence handles column widths, not undo/redo
- ❌ **Paging Changes** - Page navigation is UI state only
  - Rationale: Data is unchanged by page switching

### Data Changes That ARE Tracked
- ✅ **Cell Edits** - Value changes are tracked even while sorted/filtered
- ✅ **Row Additions** - New rows added via `AddRecord` are tracked
- ✅ **Row Deletions** - Row removals via `DeleteRecord` are tracked
- ✅ **Paste Operations** - Multi-cell clipboard operations are tracked
- ✅ **AutoFill Operations** - Fill-handle operations are tracked

### Mode Constraints
- ❌ **Normal Edit Mode** - Undo/Redo NOT supported (inline row editing)
- ❌ **Dialog Edit Mode** - Undo/Redo NOT supported (modal form editing)
- ✅ **Batch Edit Mode** - Undo/Redo FULLY supported (cell-level editing)

### Data Source Constraints
- ✅ **Static Arrays** - Full support
- ✅ **DataManager** - Full support
- ✅ **Dynamic Objects (ExpandoObject, DynamicObject)** - Full support
- ✅ **Complex Nested Data** - Full support with path resolution
- ⚠️ **Remote DataSource** - Undo/Redo works on client-side cached data only; data is not synced back to server until `SaveBatch` is called

### Column Type Constraints
- ✅ **TextBox, Numeric, Date, Checkbox** - Full support
- ✅ **Dropdown, ComboBox** - Full support
- ✅ **ForeignKey Columns** - Full support (both FK ID and display value tracked)
- ✅ **Template Columns** - Support depends on template implementation
- ⚠️ **Read-only Columns** - Cannot be edited; no undo/redo needed

### Validation & Business Rules
- ⚠️ **Validation on Undo** - Validation is BYPASSED during undo (data was valid before)
- ⚠️ **Validation on Redo** - Validation is ENFORCED during redo (new data must pass validation)
- ⚠️ **Custom Business Rules** - Application-level validation should use `ActionUndoing` and `ActionRedoing` events

### Performance Constraints
- ⚠️ **Very Large Datasets (1M+ rows)** - Undo/Redo operations may be slow; recommend reducing `UndoRedoLimit`
- ⚠️ **Large Cell Values** - Cell values with complex objects increase memory footprint; monitor stack size
- ⚠️ **Rapid Edits** - Rapid consecutive edits (>100 per second) may cause UI lag; consider grouping with `BeginActionGroup`/`EndActionGroup`

### Cross-Feature Constraints
- ⚠️ **Infinite Scrolling** - Undo/Redo supported, but may trigger server calls to reload data if undone row is outside current buffer
- ⚠️ **Virtual Scrolling** - Undo/Redo supported; virtual scroll indices recalculated after row add/delete
- ✅ **Sorting + Filtering + Grouping** - Full support; rows reorder/regroup as needed after undo

### State Persistence
- ⚠️ **No Persistence** - Undo/Redo stacks are cleared on browser refresh, page navigation, or grid disposal
- ⚠️ **No Session Recovery** - If page crashes, undo history is lost
- 💡 **Workaround** - Serialize stacks manually if persistence is needed (not built-in)

## Technical Notes

- **Implementation**: 
  - Undo/Redo history management logic resides in `Internal/Actions/Edit.cs`
  - Configuration via `GridEditSettings.cs` properties (`EnableUndoRedo`, `UndoRedoLimit`)
  - Public API methods exposed in `SfGrid.Methods.cs`
  - Event definitions in `GridEvents.cs`
  - Stack state (counts, availability) managed in `SfGrid.Properties.cs`
  - Action type enumerations in `Enumeration/GridsEnumerations.cs`
  - Event models in `EventModels/Grids.cs`

- **Dependencies**: 
  - Batch Editing mode (`EditMode.Batch`)
  - Cell Edit operations
  - Row Add/Delete operations
  - Cross-feature validation with Sorting, Filtering, Grouping, Paging, Virtual Scrolling, Frozen Columns, and Selection

- **Keyboard Integration**:
  - Ctrl+Z → UndoAsync()
  - Ctrl+Y → RedoAsync()
  - Ctrl+Shift+Z → RedoAsync() (alternative)

- **Event Lifecycle**:
  1. User action → Action added to Undo stack, Redo stack cleared
  2. User presses Ctrl+Z → ActionUndoing event → Undo reversal → ActionUndone event
  3. User presses Ctrl+Y → ActionRedoing event → Redo reapplication → ActionRedone event
  4. Batch Save/Cancel/Refresh → History cleared
