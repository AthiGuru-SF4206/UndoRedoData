## Purpose

Infinite Scroll enables the Syncfusion Blazor Grid to load large datasets on demand by
fetching the next block of records when the user scrolls to the bottom of the scrollable
area, eliminating the need for traditional pagination. It supports a default (accumulate)
mode and an optional cache mode that manages DOM rows within a bounded window. The
feature also integrates with grouping, lazy-load grouping, editing, sorting, filtering,
and other grid actions.

## Requirements

### Requirement: EnableInfiniteScrolling Flag

The grid SHALL expose an `EnableInfiniteScrolling` (`bool`, default `false`) parameter on
`SfGrid<T>`. When set to `true`, the grid loads data in page-sized blocks triggered by
scroll position instead of using standard paging navigation.

#### Scenario: Feature disabled by default
- **GIVEN** a grid rendered without setting `EnableInfiniteScrolling`
- **WHEN** the grid completes initial render
- **THEN** `EnableInfiniteScrolling` is `false` and normal paging behaviour applies

#### Scenario: Feature enabled at runtime
- **GIVEN** a grid with `EnableInfiniteScrolling="true"`
- **WHEN** the component initialises (`OnInitializedAsync`)
- **THEN** `InfiniteScrollModule` (type `InfiniteScroll<T>`) is instantiated and attached to the grid

### Requirement: InfiniteScrollSettings Configuration

The grid SHALL expose an `InfiniteScrollSettings` parameter that accepts a
`GridInfiniteScrollSettings` instance to control fine-grained infinite-scroll behaviour.

#### Scenario: Default settings applied
- **GIVEN** `EnableInfiniteScrolling` is `true` and no `<GridInfiniteScrollSettings>` child is provided
- **WHEN** the grid renders
- **THEN** `InitialBlocks` defaults to `3`, `MaximumBlocks` defaults to `3`, and `EnableCache` defaults to `false`

#### Scenario: Settings propagated to parent
- **GIVEN** a `<GridInfiniteScrollSettings>` child component is placed inside `<SfGrid>`
- **WHEN** `OnInitializedAsync` completes
- **THEN** `Parent.UpdateChildProperties("InfiniteScrollSettings", this)` is called, making the settings available on the grid

#### Scenario: Settings change at runtime
- **GIVEN** `GridInfiniteScrollSettings` parameters are updated from outside the component
- **WHEN** `OnParametersSetAsync` is called and any of `InitialBlocks`, `MaximumBlocks`, or `EnableCache` has changed
- **THEN** the backing private fields `_initialBlocks`, `_maximumBlocks`, and `_enableCache` are updated to reflect the new values

### Requirement: InitialBlocks Controls First-Load Quantity

The grid MUST load `InitialBlocks × PageSize` rows during the first data request, giving
the viewport enough content to avoid an immediately empty scroll area.

#### Scenario: Initial page query uses InitialBlocks
- **GIVEN** `EnableInfiniteScrolling` is `true` and `InitialBlocks` is `3` with `PageSize` `20`
- **WHEN** `IntialInfinitePageQuery` is called with `IsInfiniteInitialRender = true`
- **THEN** the query is paged with `Take = 60` (3 × 20)

#### Scenario: InitialBlocks clamped when EnableCache is true
- **GIVEN** `EnableCache = true`, `InitialBlocks = 5`, and `MaximumBlocks = 3`
- **WHEN** `IntialInfinitePageQuery` is called
- **THEN** `InitialBlocks` is clamped to `MaximumBlocks` (3) to prevent DOM rows exceeding the cache window

### Requirement: On-Demand Loading via Scroll

The grid SHALL request the next page of data when the JavaScript layer signals that the
vertical scrollbar has reached the bottom.

#### Scenario: Downward scroll triggers data load
- **GIVEN** `EnableInfiniteScrolling` is `true` and the user has scrolled to the bottom of the grid
- **WHEN** the JS interop method `LoadInfiniteData` is invoked with `isBottom = true`
- **THEN** `InfiniteScrollModule.GenerateInfiniteScrollDatas(action, isBottom: true, isTop: false)` is called, incrementing `CurrentPage` and appending new rows

#### Scenario: Upward scroll triggers data load in cache mode
- **GIVEN** `EnableCache = true` and the user scrolls back toward the top
- **WHEN** `LoadInfiniteData` is invoked with `isTop = true`
- **THEN** `GenerateInfiniteScrollDatas` is called with `isTop: true`, recalculates `CurrentPage` downward, and prepends the earlier block of rows

#### Scenario: Key-interaction scroll is tracked
- **GIVEN** infinite scrolling is active and the user navigates with keyboard
- **WHEN** `LoadInfiniteData` is called with `keyInteractionScroll = true`
- **THEN** `InfiniteScrollModule.KeyInteractionScroll` is set to `true` for the duration of the call and reset to `false` after `GenerateInfiniteScrollDatas` completes

### Requirement: Page Query Construction for Scroll Events

The grid MUST build the correct skip/take query for each scroll trigger based on scroll
direction, current rows in DOM, and cache settings.

#### Scenario: Downward scroll in default mode
- **GIVEN** `EnableCache = false`, current last row index is `59` (0-based), and `PageSize = 20`
- **WHEN** a downward scroll event fires
- **THEN** `CurrentPage` is set to `ceil(60 / 20) + 1 = 4` and the query fetches page 4 with `Take = PageSize`

#### Scenario: Downward scroll prevents overflow past total items
- **GIVEN** `MaximumBlocks = 3`, `PageSize = 20`, and `TotalItemCount = 55`
- **WHEN** a downward scroll would request rows beyond `TotalItemCount`
- **THEN** `query.Queries.Take` is adjusted to `TotalItemCount - query.Queries.Skip` so no extra rows are requested

#### Scenario: Mutation operations (Save/Delete/Add) rebuild query
- **GIVEN** a CRUD operation completes while infinite scrolling is active
- **WHEN** `IntialInfinitePageQuery` is called with `RequestType` in `{"Save","Delete","Add","RowDragAndDrop","PDFExport","ExcelExport","CsvExport"}`
- **THEN** in non-cache mode the query is reset to `Page(1, parentRowsCount)` to re-load all visible rows from the beginning

### Requirement: Cache Mode DOM Management

When `EnableCache = true` the grid MUST cap the number of DOM rows to
`MaximumBlocks × PageSize`, removing rows from the opposite end of the scroll direction
when the limit is exceeded.

#### Scenario: Excess rows trimmed on downward scroll
- **GIVEN** `EnableCache = true`, `MaximumBlocks = 3`, `PageSize = 20`, and the DOM contains 60+ rows
- **WHEN** a new block is appended at the bottom
- **THEN** `RemoveTopRows` removes excess rows from the top so total DOM rows ≤ `MaximumBlocks × PageSize`

#### Scenario: Excess rows trimmed on upward scroll
- **GIVEN** `EnableCache = true`, `MaximumBlocks = 3`, `PageSize = 20`, and the DOM contains 60+ rows
- **WHEN** a block is prepended at the top
- **THEN** `RemoveBottomRows` removes excess rows from the bottom so total DOM rows ≤ `MaximumBlocks × PageSize`

#### Scenario: ViewData trimmed in cache mode
- **GIVEN** `EnableCache = true` and `_infiniteCurrentViewData.Count > MaximumBlocks × PageSize`
- **WHEN** `RefreshInfiniteCurrentViewData` is called after a scroll event
- **THEN** items are removed from the leading end (downward) or trailing end (upward) to keep `_infiniteCurrentViewData` within `MaximumBlocks × PageSize` items

### Requirement: Row Cache Dictionary

The grid MUST maintain a `InfiniteGeneratedRows` dictionary keyed by row index to avoid
duplicating pre-generated rows when the same index is encountered again.

#### Scenario: New rows stored in cache
- **GIVEN** `CacheGeneratedRows` is called with a list of rows not yet in `InfiniteGeneratedRows`
- **WHEN** the method iterates over rows
- **THEN** each row is inserted at its index key and added to the returned `cachedRows` list

#### Scenario: Duplicate rows served from cache
- **GIVEN** a row at index `N` already exists in `InfiniteGeneratedRows`
- **WHEN** `CacheGeneratedRows` encounters that index again
- **THEN** the existing cached row is returned instead of the newly generated one

### Requirement: State Reset on Grid Actions

The grid MUST reset infinite-scroll internal state when data-altering actions (filter,
sort, search, refresh, group, edit) occur, so that the next render starts from the correct
scroll position.

#### Scenario: Reset on Filtering / Sorting / Searching / Refresh
- **GIVEN** an infinite-scroll grid with accumulated rows
- **WHEN** `ResetInfiniteProperties` is called with action in `{"Filtering","ClearFiltering","Sorting","ClearSorting","Searching","Refresh","Reorder","Grouping","UnGrouping"}`
- **THEN** `IsInfiniteInitialRender` is set to `true`, `_infiniteCurrentViewData` is cleared, `InfiniteGeneratedRows` is cleared, and `CurrentPage` is reset to `1`

#### Scenario: Reset on CRUD Add (cache mode)
- **GIVEN** `EnableCache = true` and a new record is being added at a page other than page 1
- **WHEN** `ResetInfiniteProperties("Add")` or `ResetInfiniteProperties("Save")` is called for an add operation
- **THEN** `CurrentPage` is set to `1` and `InfiniteGeneratedRows` is cleared so the new row appears at the top

#### Scenario: Reset on Delete
- **GIVEN** a record is deleted from an infinite-scroll grid
- **WHEN** `ResetInfiniteProperties("Delete")` is called
- **THEN** `_infiniteCurrentViewData` is cleared and `InfiniteGeneratedRows` is cleared; `CurrentPage` is not changed (preserves scroll position)

#### Scenario: Reset on GroupExpandCollapseAll
- **GIVEN** grouping is active and the user collapses or expands all groups
- **WHEN** `ResetInfiniteProperties("GroupExpandCollapseAll")` is called
- **THEN** `InfiniteForceRefresh` is set to `true` (non-lazy grouping only), `CurrentPage` resets to `1`, and `InfiniteGeneratedRows` is cleared

### Requirement: Grouping Integration

The grid SHALL support infinite scrolling with both standard grouping and lazy-load
grouping. In standard grouping mode, rows are stored in `GeneratedInfiniteGroupedRows`
and managed via `SetCurrentGroupedRows`.

#### Scenario: Grouped rows accumulated on downward scroll
- **GIVEN** grouping is active with `EnableLazyLoading = false` and the user scrolls down
- **WHEN** `SetCurrentGroupedRows` is called with `IsDownScroll = true`
- **THEN** new visible rows from `GeneratedInfiniteGroupedRows` are appended to `_parent.Rows`

#### Scenario: Grouped rows prepended on upward scroll
- **GIVEN** grouping is active and the user scrolls up
- **WHEN** `SetCurrentGroupedRows` is called with `IsUpScroll = true`
- **THEN** the appropriate slice is inserted at position 0 in `_parent.Rows` based on the first visible row index

#### Scenario: Cache trims grouped rows
- **GIVEN** `EnableCache = true` and `IsDownScroll = true`
- **WHEN** `SetCurrentGroupedRows` finishes appending rows
- **THEN** `RefreshInfiniteCacheRows` is called and trims top rows to keep total rows within `MaximumBlocks × PageSize`

### Requirement: Lazy-Load Grouping Child Data

When grouping has `EnableLazyLoading = true`, the grid MUST load child rows on demand
within an expanded group caption row as the user scrolls through child records.

#### Scenario: Child rows loaded on lazy scroll
- **GIVEN** a group caption row is expanded and not all child rows are rendered
- **WHEN** `LoadInfiniteData` is invoked with `isLazyLoadChild = true` and `lastRowUid` pointing to the last visible child
- **THEN** `LoadLazyLoadChildData` fetches the next `LazyLoadPageSize` children from the group's data and inserts them after the last rendered child row

#### Scenario: Lazy load page size calculated from grid height
- **GIVEN** `EnableLazyLoading = true` and a grid `Height` is set
- **WHEN** `SetLazyLoadPageSize` is called
- **THEN** `LazyLoadPageSize = floor(Height / RowHeight) * 3` and `LazyLoadBlockSize = ceil(LazyLoadPageSize / 2)`

#### Scenario: Middle and last CSS markers applied
- **GIVEN** a group has more children than `LazyLoadPageSize`
- **WHEN** new child rows are inserted
- **THEN** the row at index `LazyLoadBlockSize` receives CSS class `e-lazyload-middle-down` and the row at `LazyLoadPageSize - 1` receives `e-lazyload-last-down`

### Requirement: Editing Integration

The grid MUST correctly handle CRUD operations (inline, dialog, batch) while infinite
scrolling is active, preserving row position and cache consistency.

#### Scenario: Add in cache mode resets to page 1
- **GIVEN** `EnableCache = true`, `CurrentPage > 1`, and a new record is added
- **WHEN** the save action completes in add mode
- **THEN** `InfiniteScrollModule.RequestType` is set to `"Save"`, `ResetInfiniteProperties` is called, and `CurrentPage` resets to `1`

#### Scenario: CurrentRowIndex reset on row cancel/save
- **GIVEN** an edit operation is in progress
- **WHEN** the edit is cancelled or saved
- **THEN** `InfiniteScrollModule.CurrentRowIndex` is reset to `0`

#### Scenario: IsInfiniteInitialRender flag reset on Save/Delete
- **GIVEN** a save or delete completes
- **WHEN** the post-action refresh fires
- **THEN** `IsInfiniteInitialRender` is set to `true` so the next query rebuilds from the correct offset

## Technical Notes

- **Implementation**:
  - `GridInfiniteScrollSettings.razor.cs` — Settings component (InitialBlocks, MaximumBlocks, EnableCache)
  - `Internal/Actions/InfiniteScroll.cs` — Core engine: query building, row accumulation, cache management, lazy-group handling
  - `SfGrid.Properties.cs` — `EnableInfiniteScrolling` and `InfiniteScrollSettings` parameters
  - `SfGrid.Lifecycle.cs` — Module instantiation and parameter sync
  - `Internal/Base/GridJSInteropAdaptor.cs` — `LoadInfiniteData` JS-invokable entry point
  - `Internal/Actions/Data.cs` — Calls `IntialInfinitePageQuery` to configure the outgoing query
  - `Internal/Actions/Edit.cs` — Resets infinite state after CRUD operations
  - `Internal/Actions/Group.cs` — Integrates grouped-row generation with infinite scroll

- **JS Interop Entry Point**: `LoadInfiniteData` (`[JSInvokable]`) in `GridJSInteropAdaptor.cs`; called by `sf-grid.js` when scroll position hits the bottom or top boundary.

- **Dependencies**:
  - `GridPageSettings` — `CurrentPage` and `PageSize` drive every skip/take calculation
  - `GroupModule` — Row generation and lazy-load expand/collapse for grouped infinite scroll
  - `VirtualScrollModule` — Shares `CurrentRowIndex` tracking with keyboard navigation
  - `EditModule` — Signals add/save/delete to `InfiniteScrollModule` for state reset
  - `EventAggregator` — `"ContentStateChanged"` event triggers re-render of content rows after lazy-load child inserts

- **Constraints**:
  - `EnableInfiniteScrolling` and `AllowPaging` are mutually exclusive — setting both is undefined behaviour.
  - When `EnableCache = true`, `InitialBlocks` MUST NOT exceed `MaximumBlocks`; the engine auto-clamps it.
  - Horizontal virtual scrolling is handled by `VirtualScrollModule` and is independent of this feature.
