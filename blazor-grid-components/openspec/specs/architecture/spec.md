## Purpose

The architecture domain describes how `SfGrid<TValue>` is structured internally as a partial, module-driven component. It captures composition boundaries across lifecycle, rendering, action modules, and JS interop integration.

## Requirements

### Requirement: PartialClassSegmentation

The grid implementation SHALL be segmented across partial class files by concern.

#### Scenario: LifecycleAndPropertiesAreSeparated
- **GIVEN** `SfGrid<TValue>` source files
- **WHEN** file responsibilities are inspected
- **THEN** lifecycle logic SHALL reside in `SfGrid.Lifecycle.cs` and parameter/property declarations SHALL reside in `SfGrid.Properties.cs`

#### Scenario: PublicMethodsSeparatedFromLifecycle
- **GIVEN** `SfGrid.Methods.cs`
- **WHEN** callable APIs are inspected
- **THEN** public operational methods SHALL be maintained outside lifecycle initialization files

### Requirement: ModuleBasedComposition

The grid MUST compose runtime behavior through dedicated module instances initialized from the root component.

#### Scenario: CoreActionModulesWiredAtInitialization
- **GIVEN** `OnInitializedAsync`
- **WHEN** module creation occurs
- **THEN** modules such as `SortModule`, `GroupModule`, `FilterModule`, `SelectionModule`, and `EditModule` SHALL be instantiated with the grid instance

#### Scenario: VirtualizationModulesWiredAtInitialization
- **GIVEN** `OnInitializedAsync`
- **WHEN** scrolling infrastructure is initialized
- **THEN** `VirtualScrollModule` and `InfiniteScrollModule` SHALL be created and retained on the grid

### Requirement: RenderLayerSeparation

The render architecture SHALL separate header/content/pager/dialog concerns into internal renderer components.

#### Scenario: HeaderAndContentRendererSelection
- **GIVEN** the grid render tree in `Internal/SfGrid.razor`
- **WHEN** virtualization flags are evaluated
- **THEN** the grid SHALL render either standard (`GridHeader`/`GridContent`) or virtual (`GridVirtualHeader`/`GridVirtualContent`) renderer components

#### Scenario: DialogEditingRendererBoundary
- **GIVEN** edit mode is dialog
- **WHEN** render conditions are evaluated
- **THEN** dialog editing SHALL be rendered through `DialogEdit` instead of inline content replacement

### Requirement: EventAggregatorIntegration

The architecture SHOULD use event aggregation for internal cross-module communication.

#### Scenario: PagingCountBroadcast
- **GIVEN** paging is enabled
- **WHEN** pager is prepared during render
- **THEN** the grid SHALL trigger `EventAggregator.Trigger("GetPageCount", ...)` before rendering `SfPager`

#### Scenario: DataBoundDispatchPath
- **GIVEN** data-bound invocation is required after render
- **WHEN** `_requireDataBoundInvoke` is processed
- **THEN** the grid SHALL invoke `GridEvents.DataBound` or fallback internal dispatch paths for host integrations

### Requirement: JavaScriptInteropBoundary

The architecture SHALL isolate browser-side operations behind grid interop adapters and method wrappers.

#### Scenario: GridJsAdaptorUsedForClientIntegration
- **GIVEN** module initialization
- **WHEN** interop infrastructure is established
- **THEN** `_jsAdaptor` SHALL be initialized as the component-side bridge

#### Scenario: LifecycleInvokesInteropForStateTransitions
- **GIVEN** specific property changes (for example virtualization toggles)
- **WHEN** `OnParametersSetAsync` processes those changes
- **THEN** the grid SHALL call client-side interop methods through `InvokeMethod`
