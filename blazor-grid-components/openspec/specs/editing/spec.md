## Purpose

The editing domain controls all CRUD (Create, Read, Update, Delete) operations for the Syncfusion Blazor Grid. It supports three editing modes — Normal (inline row editing), Dialog, and Batch (cell-level editing) — and governs the entire lifecycle from initiating an edit through validation to persisting the final change. This specification documents both row-level and batch-level editing behavior implemented by the grid.

---

## Requirements

### Requirement: EnableEditing

The grid's editing capability SHALL be activated only when `GridEditSettings.AllowEditing` is `true`. Editing SHALL be disabled by default.

#### Scenario: EditingDisabledByDefault
- **GIVEN** a grid with no `<GridEditSettings>` component configured
- **WHEN** a user double-clicks a row
- **THEN** no edit form is rendered and `Parent.IsEdit` remains `false`

#### Scenario: EditingEnabledViaParameter
- **GIVEN** `<GridEditSettings AllowEditing="true">` is set
- **WHEN** a user double-clicks a row (and `AllowEditOnDblClick` is `true`)
- **THEN** `StartEdit` is invoked, the row enters edit state, and `Parent.IsEdit` is set to `true`

---

### Requirement: EditMode

The grid SHALL support three editing modes controlled by `GridEditSettings.Mode`:
- `EditMode.Normal` (default) — inline row editing form rendered as a table row
- `EditMode.Dialog` — editing form rendered inside a `SfDialog`
- `EditMode.Batch` — individual cell editing without a row-level form

#### Scenario: NormalModeInlineForm
- **GIVEN** `Mode="EditMode.Normal"` and `AllowEditing="true"`
- **WHEN** a row is activated for editing via `StartEdit`
- **THEN** `Row.IsEdit` is set to `true`, a content state change is triggered, and the edit form renders inline in the grid body

#### Scenario: DialogModeTriggersDialog
- **GIVEN** `Mode="EditMode.Dialog"` and `AllowEditing="true"`
- **WHEN** `StartEdit` completes without cancellation
- **THEN** the `ShowDialog` event is triggered via the event aggregator instead of a content state change

#### Scenario: BatchModeCellEditing
- **GIVEN** `Mode="EditMode.Batch"` and `AllowEditing="true"`
- **WHEN** a user double-clicks a specific cell
- **THEN** `EditCell` is invoked, only that cell enters edit state (`Cell.IsEdit = true`), and the row is not fully replaced with an edit form

---

### Requirement: StartEditLifecycle

When entering edit mode for Normal or Dialog, the grid SHALL follow a defined event sequence and SHALL abort if any event is cancelled.

#### Scenario: BeforeRowEditStartCancel
- **GIVEN** a handler for `GridEvents.OnRowEditStart` that sets `Cancel = true`
- **WHEN** double-click triggers `StartEdit`
- **THEN** `StartEdit` returns early, `Parent.IsEdit` remains `false`, and no row is marked as editing

#### Scenario: RowEditingEventCancel
- **GIVEN** a handler for `GridEvents.RowEditing` that sets `Cancel = true`
- **WHEN** `StartEdit` reaches the `RowEditing` event
- **THEN** `StartEdit` returns early; if `ShowAddNewRow` is enabled, a `ResetAddFormValues` event is triggered

#### Scenario: FullStartEditSuccess
- **GIVEN** no cancellation handlers are registered
- **WHEN** `StartEdit` is called for a data row
- **THEN** the event sequence fires in order:
  1. `OnActionBegin` (RequestType = `BeforeBeginEdit`)
  2. `OnRowEditStart`
  3. `OnBeginEdit`
  4. `OnActionBegin` (RequestType = `BeginEdit`)
  5. `RowEditing`
  6. Row state changes are triggered
  7. `OnActionComplete`
  8. `RowEdited`

### Requirement: AddRecord

The grid SHALL support adding new records when `GridEditSettings.AllowAdding` is `true`. A new blank row model SHALL be generated and inserted into `Parent.Rows`.

#### Scenario: AddAtTop
- **GIVEN** `AllowAdding="true"` and `NewRowPosition="NewRowPosition.Top"`
- **WHEN** `AddRecord` is invoked
- **THEN** a new empty row is inserted at index 0 in `Parent.Rows`, `Row.IsAddedTop` is set to `true`, and `Parent.IsAdd` is `true`

#### Scenario: AddAtBottom
- **GIVEN** `AllowAdding="true"` and `NewRowPosition="NewRowPosition.Bottom"`
- **WHEN** `AddRecord` is invoked
- **THEN** a new empty row is appended to the end of `Parent.Rows`, `Row.IsAddedBottom` is set to `true`

#### Scenario: AddWhileEditingBlocked
- **GIVEN** `Parent.IsEdit` is already `true` (a row is being edited)
- **WHEN** `AddRecord` is invoked
- **THEN** the new record is not added; `AddRecord` returns immediately

#### Scenario: AddRecordEventSequence
- **GIVEN** `AllowAdding="true"` and no cancellation handlers
- **WHEN** `AddRecord` is invoked
- **THEN** the events fire in order:
  1. `OnActionBegin` (RequestType = `Add`)
  2. `RowCreating`
  3. Selection is cleared (if PersistSelection is false)
  4. `OnActionComplete`
  5. `RowCreated`

#### Scenario: AddRecordCancelledByEvent
- **GIVEN** a handler for `GridEvents.RowCreating` that sets `Cancel = true`
- **WHEN** `AddRecord` is triggered
- **THEN** no row is inserted into `Parent.Rows` and `Parent.IsEdit` remains `false`

---

### Requirement: DefaultValues

When a new row is added, the grid SHALL apply `DefaultValue` from each `GridColumn` to the new record before rendering the edit form.

#### Scenario: ColumnDefaultValueApplied
- **GIVEN** a `GridColumn` with `DefaultValue="SomeDefault"` and a new add action
- **WHEN** `SetDefaultValue` is called during `AddRecord`
- **THEN** the new record's field matching the column's `Field` is set to `SomeDefault` via `SetValue`

---

### Requirement: SaveRecord

When an edited record is submitted, the grid SHALL validate all fields, raise appropriate events, and persist the data if validation passes.

#### Scenario: ValidationFailureBlocksSave
- **GIVEN** a row in edit state with an invalid field value
- **WHEN** `EndEdit` is called
- **THEN** `EditContext.Validate()` returns `false`, validation messages are rendered, and `ModelChanged` is NOT called

#### Scenario: SaveActionEventSequence
- **GIVEN** a valid edited record in Normal mode
- **WHEN** `EndEdit` is called
- **THEN** the events fire in order:
  1. `OnActionBegin` (RequestType = `Save`, Action = "Edit" or "Add")
  2. `RowUpdating`
  3. Data is persisted via `ModelChanged`
  4. Row selection is restored

#### Scenario: SaveCancelledByEvent
- **GIVEN** a handler for `GridEvents.RowUpdating` that sets `Cancel = true`
- **WHEN** `EndEdit` fires and reaches `ModelChanged`
- **THEN** the save operation aborts; `Parent.IsEdit` remains `true` (unless `ShowAddNewRow` is active)

#### Scenario: TabKeyNavigationAfterSave
- **GIVEN** Normal mode editing with the last cell focused in a non-last row
- **WHEN** Tab key is pressed to trigger `EndEdit`
- **THEN** after save, the next row (rowIndex + 1) is selected via `SelectRowAsync`

#### Scenario: ShiftTabKeyNavigationAfterSave
- **GIVEN** Normal mode editing with the first cell focused in a non-first row
- **WHEN** Shift+Tab triggers `EndEdit`
- **THEN** after save, the previous row (rowIndex - 1) is selected via `SelectRowAsync`

---

### Requirement: CancelEdit

The grid SHALL support cancelling an active edit, discarding all unsaved changes and restoring the original row state.

#### Scenario: CancelNormalModeEdit
- **GIVEN** a row is in edit state in Normal mode (`Parent.IsEdit = true`)
- **WHEN** `CloseEdit` is called (e.g., Escape key)
- **THEN**:
  1. `EditCanceling` event is raised
  2. If not cancelled, the edited row's `IsEdit` is set to `false`
  3. If adding, the row is removed from `Parent.Rows`
  4. `Parent.IsEdit` is set to `false`
  5. `OnActionComplete` (RequestType = `Cancel`) is raised
  6. `EditCanceled` event is raised

#### Scenario: CancelBlockedByEvent
- **GIVEN** a handler for `GridEvents.EditCanceling` that sets `Cancel = true`
- **WHEN** `CloseEdit` is called
- **THEN** the cancel operation aborts; the row remains in edit state

---

### Requirement: DeleteRecord

The grid SHALL support deleting a selected record when `GridEditSettings.AllowDeleting` is `true`.

#### Scenario: DeleteSelectedRow
- **GIVEN** `AllowDeleting="true"` and a row is selected
- **WHEN** `DeleteRecord` is called
- **THEN** the row's `Action` is set to `EditAction.Deleted`, a `RowDeletingEventArgs` is raised, and the deletion is processed via `ModelChanged`

#### Scenario: DeleteByData
- **GIVEN** a specific data object and field name are passed to `DeleteRecord`
- **WHEN** `DeleteRecord(fieldname, data)` is called
- **THEN** the matching row is located via primary key lookup and marked as deleted

---

### Requirement: ColumnEditability

The grid SHALL enforce per-column editing rules. A column SHALL NOT be editable if any of the following conditions are met:

- `GridColumn.AllowEditing` is `false` (unless adding and `AllowAdding` is `true`)
- `GridColumn.IsPrimaryKey` is `true` and the action is not an add
- `GridColumn.IsIdentity` is `true`
- `GridColumn.AllowAdding` is `false` and the action is an add
- The column is not `Visible`

#### Scenario: PrimaryKeyNotEditableOnEdit
- **GIVEN** a column with `IsPrimaryKey="true"` and an existing row is being edited
- **WHEN** `isEditable(column)` is evaluated
- **THEN** the method returns `false` and the cell renders as read-only

#### Scenario: IdentityColumnAlwaysReadOnly
- **GIVEN** a column with `IsIdentity="true"`
- **WHEN** `isEditable(column)` is evaluated for any action
- **THEN** the method returns `false`

#### Scenario: AllowEditingFalseWithAllowAddingTrue
- **GIVEN** a column with `AllowEditing="false"` and `AllowAdding="true"`
- **WHEN** a new row is being added and `isEditable(column)` is called
- **THEN** the method returns `true` (the column is editable during add)

### Requirement: EditCellEditors

The grid SHALL render the appropriate editor component for each column type in the edit form.

| Column Type | Editor Component |
|---|---|
| `string` | `TextBoxEditCell` |
| `number` (double, int, decimal, etc.) | `NumericEditCell` |
| `DateTime`, `DateOnly` | `DatePickerEditCell` |
| `TimeOnly` | `TimePickerEditCell` |
| `bool` | `BooleanEditCell` |
| ForeignKey column | `ForeignKeyEditCell` |
| Enum / configured list | `DropDownEditCell` |
| Custom `EditTemplate` | Renders the `RenderFragment` directly |

#### Scenario: TextBoxRenderedForStringColumn
- **GIVEN** a `GridColumn` with `Type="ColumnType.String"` and no `EditTemplate`
- **WHEN** a row enters edit mode
- **THEN** a `TextBoxEditCell` component is rendered for that column's cell

#### Scenario: CustomEditTemplateOverridesDefault
- **GIVEN** a `GridColumn` with a non-null `EditTemplate` property
- **WHEN** a row enters edit mode
- **THEN** the custom `RenderFragment` is rendered instead of any default editor component

### Requirement: ValidationIntegration

The grid SHALL integrate Blazor's `EditContext` / `DataAnnotationsValidator` for form validation during Normal and Dialog editing.

#### Scenario: EditContextCreatedOnStartEdit
- **GIVEN** a row is activated for editing via `StartEdit`
- **WHEN** `EnsureDataAndEditContext` is called with the cloned row data
- **THEN** a new `EditContext` is created wrapping the cloned data object

#### Scenario: ComplexFieldValidationContext
- **GIVEN** columns with dot-notation fields (e.g., `"Address.City"`)
- **WHEN** an edit form is opened
- **THEN** a separate `EditContext` for each complex parent object is stored in `ComplexEditContext` keyed by the field path

#### Scenario: ValidationErrorPreventsRender
- **GIVEN** a validation error is reported via `ApplyFormValidation`
- **WHEN** `ErrorResult` count is greater than zero
- **THEN** the validation tooltip is displayed via `InvokeValidation` and `ShowValidationMessage` is triggered

#### Scenario: InvalidDataContextThrows
- **GIVEN** the grid cannot create or infer an `EditContext` from the row data type `T`
- **WHEN** `EnsureDataAndEditContext` is called with `null` data
- **THEN** an `InvalidOperationException` is thrown with a descriptive message

### Requirement: ShowAddNewRow

When `GridEditSettings.ShowAddNewRow` is `true`, the grid SHALL permanently display an empty add form row at the top or bottom of the content area, independent of the normal add action flow.

#### Scenario: AddNewRowAlwaysVisible
- **GIVEN** `ShowAddNewRow="true"` and `AllowAdding="true"`
- **WHEN** the grid renders
- **THEN** an empty edit row is always visible without requiring the user to click an "Add" button

#### Scenario: AddNewRowDisabledWhenAllowAddingFalse
- **GIVEN** `ShowAddNewRow="true"` and `AllowAdding="false"`
- **WHEN** the grid renders
- **THEN** the add form row is displayed but all its cells are disabled

---

### Requirement: NewRowPosition

The position of a newly added row SHALL be determined by `GridEditSettings.NewRowPosition`. The default is `NewRowPosition.Top`.

#### Scenario: TopPositionIsDefault
- **GIVEN** `<GridEditSettings AllowAdding="true">` with no explicit `NewRowPosition`
- **WHEN** `AddRecord` is called
- **THEN** the new row is inserted at index 0

#### Scenario: BottomPositionAppends
- **GIVEN** `NewRowPosition="NewRowPosition.Bottom"`
- **WHEN** `AddRecord` is called
- **THEN** the new row is appended after the last existing row

---

### Requirement: AllowEditOnDblClick

When `GridEditSettings.AllowEditOnDblClick` is `false`, the grid SHALL NOT initiate editing on a row double-click.

#### Scenario: DblClickEditDisabled
- **GIVEN** `AllowEditing="true"` and `AllowEditOnDblClick="false"`
- **WHEN** a user double-clicks a row
- **THEN** `DblClickHandler` does not call `StartEdit` and the row remains in read-only state

#### Scenario: DblClickEditEnabled
- **GIVEN** `AllowEditing="true"` and `AllowEditOnDblClick="true"` (default)
- **WHEN** a user double-clicks a row
- **THEN** `DblClickHandler` calls `StartEdit` for Normal mode or `EditCell` for Batch mode

---

### Requirement: VirtualizationEditSupport

When `EnableVirtualization` or `EnableInfiniteScrolling` is active, the grid SHALL scroll to the edited row if it is outside the current viewport before or after validation.

#### Scenario: ScrollToEditedRowOnValidationFail
- **GIVEN** `EnableVirtualization="true"` and an edited row that is outside the rendered range
- **WHEN** validation fails during `EndEdit`
- **THEN** `VirtualScrollModule.ScrollToEditedRowAsync` is called to bring the row into view

#### Scenario: InfiniteScrollScrollsToEditedRow
- **GIVEN** `EnableInfiniteScrolling="true"` and a paged edit scenario
- **WHEN** validation fails during `EndEdit`
- **THEN** `sfBlazor.Grid.scrollIntoView` JS interop is invoked with the edited row's index

---

### Requirement: BatchEditingConfiguration

When `GridEditSettings.Mode` is set to `EditMode.Batch`, the grid SHALL perform cell-level editing and SHALL respect batch confirmation behavior through `GridEditSettings.ShowConfirmDialog`.

#### Scenario: BatchSaveUsesConfirmDialog
- **GIVEN** `Mode="EditMode.Batch"`, pending dirty cells, and `ShowConfirmDialog="true"`
- **WHEN** `EndEdit` is invoked
- **THEN** the grid SHALL set `AlertMessage` to `BatchSaveConfirm` and trigger `ShowValidationDialog` instead of immediately persisting

#### Scenario: BatchSaveSkipsConfirmDialog
- **GIVEN** `Mode="EditMode.Batch"`, pending dirty cells, and `ShowConfirmDialog="false"`
- **WHEN** `EndEdit` is invoked
- **THEN** the grid SHALL call `BatchSave` directly

#### Scenario: BatchCancelUsesConfirmDialog
- **GIVEN** `Mode="EditMode.Batch"`, `HasBatchChanges=true`, `ShowConfirmDialog="true"`, and cancel is not via escape key
- **WHEN** `CloseEdit` is invoked
- **THEN** the grid SHALL set `AlertMessage` to `CancelEdit`, trigger `ShowValidationDialog`, and defer discard until confirmation

---

### Requirement: BatchCellEditLifecycle

In batch mode, cell editing SHALL be executed as a cell-scoped lifecycle (`EditCell` -> `SaveCell`) with cancellable events.

#### Scenario: CellEditCanBeCancelled
- **GIVEN** `OnCellEdit` handler sets `Cancel = true`
- **WHEN** the grid attempts to enter a cell edit state
- **THEN** the target cell SHALL NOT enter edit mode

#### Scenario: CellSaveCanBeCancelled
- **GIVEN** a dirty batch cell and `OnCellSave` handler sets `Cancel = true`
- **WHEN** `SaveCell` runs
- **THEN** the current edit SHALL be aborted and `CellSaved` SHALL NOT be raised

#### Scenario: CellSavedRaisedAfterSuccessfulSave
- **GIVEN** a dirty batch cell with no save cancellation
- **WHEN** `SaveCell` completes successfully
- **THEN** `CellSaved` SHALL be invoked and the edited row/cell SHALL remain marked dirty for batch commit

---

### Requirement: BatchAddDeleteAndDirtyTracking

Batch mode SHALL track pending changes on rows and cells using dirty flags and edit actions.

#### Scenario: BatchAddCreatesDirtyAddedRow
- **GIVEN** `Mode="EditMode.Batch"` and adding is allowed
- **WHEN** `BulkAddRow` is executed
- **THEN** a generated row SHALL be inserted at configured position, row action SHALL be `EditAction.Added`, row/cells SHALL be marked dirty, and `HasBatchChanges` SHALL be `true`

#### Scenario: BatchDeleteMarksRowsDeleted
- **GIVEN** one or more selected rows in batch mode
- **WHEN** batch delete is executed
- **THEN** affected rows SHALL be marked `IsDirty=true` and `Action=EditAction.Deleted` without immediate datasource commit

#### Scenario: BatchChangesCategorizedByEditAction
- **GIVEN** batch mode with mixed dirty rows
- **WHEN** `GetBatchChanges` is called
- **THEN** rows marked `Deleted` SHALL populate `DeletedRecords`, rows marked `Added` SHALL populate `AddedRecords`, and other dirty rows SHALL populate `ChangedRecords`

---

### Requirement: BatchSaveLifecycle

Batch save SHALL execute a cancellable pre-save event and persist all accumulated changes as a single logical save operation.

#### Scenario: BatchSaveCancelledByEvent
- **GIVEN** `OnBatchSave` handler sets `Cancel = true`
- **WHEN** `BatchSave` is invoked
- **THEN** persistence SHALL stop before `DataModule.SaveChanges`

#### Scenario: BatchSavePersistsAndResetsDirtyState
- **GIVEN** pending batch changes and no cancellation
- **WHEN** `BatchSave` successfully completes
- **THEN** `DataModule.SaveChanges` SHALL be called with primary key and `BatchChanges`, `HasBatchChanges` SHALL become `false`, row/cell dirty flags SHALL be reset, and `DataProcess` SHALL run with request type `Action.BatchSave`

---

### Requirement: BatchCancelLifecycle

Batch cancel SHALL support pre-cancel interception and SHALL restore non-committed UI state.

#### Scenario: BatchCancelCancelledByEvent
- **GIVEN** `OnBatchCancel` handler sets `Cancel = true`
- **WHEN** `BatchClose` is invoked
- **THEN** batch discard SHALL stop and dirty state SHALL remain

#### Scenario: BatchCancelClearsPendingAddsAndDirtyFlags
- **GIVEN** pending batch changes and cancel proceeds
- **WHEN** `BatchClose` runs without escape-key short-circuit
- **THEN** temporary added rows (`IsAddedTop`/`IsAddedBottom`) SHALL be removed, edited row snapshots SHALL be cleared, dirty flags SHALL be reset, and toolbar/content state SHALL be refreshed

---

### Requirement: BatchProgrammaticAPIs

The grid public API SHALL expose batch-specific methods that are active in batch mode.

#### Scenario: EditCellAsyncRequiresBatchMode
- **GIVEN** `EditCellAsync(index, fieldName)` is called
- **WHEN** mode is not `EditMode.Batch` or editing is disallowed
- **THEN** no edit action SHALL be performed

#### Scenario: GetBatchChangesAsyncReturnsCurrentDiff
- **GIVEN** pending batch edits exist
- **WHEN** `GetBatchChangesAsync()` is called
- **THEN** the method SHALL return added, changed, and deleted collections derived from current row state

#### Scenario: ApplyBatchChangesAsyncAppliesVisualBatchState
- **GIVEN** batch mode and a non-null `BatchChanges<TValue>` payload
- **WHEN** `ApplyBatchChangesAsync` is called
- **THEN** added/edited/deleted records SHALL be projected into row/cell dirty state and toolbar/content state SHALL be refreshed

#### Scenario: CloseEditAsyncCancelsBatchState
- **GIVEN** batch mode is active
- **WHEN** `CloseEditAsync()` is invoked
- **THEN** the grid SHALL route to batch cancel behavior (`BatchClose`), including confirmation flow when configured

## Technical Notes

- **Implementation**: `Internal/Actions/Edit.cs`, `GridEditSettings.cs`, `Internal/Editors/EditorCellBase.cs`, `Internal/Editors/*.razor`
- **Edit modes**: `EditMode.Normal`, `EditMode.Dialog`, `EditMode.Batch` (defined in `Enumeration/GridsEnumerations.cs`)
- **New row positions**: `NewRowPosition.Top` (default), `NewRowPosition.Bottom`
- **Row model generation**: `Edit<T>.GetModelGenerator()` delegates to `RowModelGenerator<T>` or `GroupModelGenerator<T>` depending on grouping state
- **Data cloning**: `CloneRowData` supports `ExpandoObject`, `DynamicObject`, and static CLR types; complex fields are individually cloned and set via `SetValue`
- **EditContext propagation**: `EnsureDataAndEditContext` allows external override via `OnActionBegin`, `RowCreating`, `RowEditing`, `OnBatchAdd`, and `OnCellEdit` event args
- **Validation error tracking**: `ErrorResult` (List<ValidationResult>) and `position` (Dictionary<string,object>) track active errors; `ClearRules()` resets both
- **Dependencies**: `Selection` (ClearSelectionAsync), `VirtualScroll`/`InfiniteScroll` (scroll interop), `FocusHandler` (Focus/ClearCurrent), `ReactiveAggregate` (aggregate refresh on save/delete), `Data` (ModelChanged, DataModule.SaveChanges)
- **Events raised** (Normal mode lifecycle):

| Phase | Event |
|---|---|
| Before begin edit | `OnActionBegin` (BeforeBeginEdit), `OnRowEditStart` |
| Begin edit | `OnBeginEdit`, `OnActionBegin` (BeginEdit), `RowEditing` |
| Edit complete | `OnActionComplete`, `RowEdited` |
| Before add | `OnActionBegin` (Add), `RowCreating` |
| Add complete | `OnActionComplete`, `RowCreated` |
| Before save | `OnActionBegin` (Save), `RowUpdating` |
| Before cancel | `OnActionBegin` (Cancel), `EditCanceling` |
| Cancel complete | `OnActionComplete`, `EditCanceled` |
| Before delete | `OnActionBegin` (Delete), `RowDeleting` |
